# Подготовка к защите

## Что рассказать о проекте

«Я использую Kotlin и Spring Boot. Приложение хранит личные заметки в файловой H2.
POST /auth/login проверяет пароль BCrypt и выдаёт JWT. Spring Security проверяет подпись
и claims токена на защищённых запросах. Контроллер получает проверенный Jwt, а репозиторий
ограничивает SQL-запрос текущим владельцем. API позволяет войти, создать и прочитать заметки».

Покажите отказ без токена, успешный вход, SQLi в логине, заметку со script и отсутствие
заметки у второго пользователя. Затем покажите реальные отчёты CI для того же коммита.

## Почему BCrypt, а не SHA-256?

SHA-256 быстро вычисляется, что облегчает массовый перебор после утечки хэшей.
BCrypt специально увеличивает стоимость проверки и использует случайную соль. В проекте
cost=12. Соль и параметр стоимости хранятся в строке хэша; соль не обязана быть секретной.
Пароль не расшифровывается: PasswordEncoder.matches проверяет кандидат.

У BCrypt есть ограничение 72 байта, поэтому более длинный пароль отклоняется. Байты UTF-8
и символы - не одно и то же. Для нового аккаунта дополнительно требуется минимум 15 символов.
Argon2id также является подходящим вариантом специализированного хэширования паролей.

## SAST, DAST и SCA

SAST исследует код без запуска целевого сервиса. SpotBugs/Find Security Bugs анализирует
JVM-байткод, поэтому сначала нужна компиляция Kotlin. Сканер не доказывает правильность
всей бизнес-логики и может находить ложные срабатывания. В проекте выбрана категория SECURITY.

DAST взаимодействует с работающим сервисом и наблюдает ответы. Отдельные запросы curl
проверяют конкретные сценарии, но не являются полноценным DAST-аудитом.
SCA проверяет прямые и транзитивные зависимости по известным уязвимостям; здесь это OWASP Dependency-Check
для runtimeClasspath. Зависимости сборки и тестов этим SCA-шагом не охвачены.

## Как работает JWT?

JWT состоит из header, payload и signature. Base64URL не шифрует payload. HMAC-SHA256
с серверным секретом защищает целостность; держатель секрета может и проверять, и выпускать JWT.
`sub` - ID пользователя, `iat` - время выпуска, `nbf` - начало допустимости,
`exp` - конец, `iss` - издатель, `aud` - аудитория. Пароль в JWT отсутствует.

NimbusJwtDecoder доверяет только HS256. Валидаторы проверяют подпись, обязательные claims,
временные границы без дополнительного допуска, издателя, аудиторию и наличие пользователя в БД.
Токен живёт 15 минут. Просто декодировать payload недостаточно для проверки подлинности.

JWT можно украсть и использовать до истечения срока. Индивидуального отзыва здесь нет;
смена общего ключа инвалидирует все прежние токены, удаление пользователя - его токены.
Для внешней сети нужен HTTPS: подпись JWT не шифрует транспорт.

## Чем опасны непроверенные библиотеки?

Уязвимость может находиться в прямой или вложенной зависимости и приводить к обходу
проверок, утечке, выполнению кода или отказу в обслуживании. SCA помогает найти известные
проблемы и обновить версии. Зелёный отчёт относится к конкретным версиям и базе на дату
запуска; он не исключает неизвестные уязвимости или вредоносный код.

## Дополнительные вопросы

**SQLi:** SQL-текст фиксирован; значения передаются через ? / PreparedStatement.
Строка `alice' OR 1=1 --` не становится частью SQL-условия.

**Авторизация:** JWT устанавливает личность. WHERE owner_id = ? определяет доступ к данным.
owner_id не принимается из тела запроса. Это отдельные этапы защиты.

**XSS:** HtmlUtils.htmlEscape кодирует текст на границе выдачи. JSON сам по себе не HTML;
XSS зависит от последующей интерпретации клиентом. Для разных контекстов нужны разные
способы вывода. Экранирование не даёт разрешения вставлять данные в любой JavaScript/URL.

**Почему CSRF отключён:** приложение не использует cookie/session/Basic-аутентификацию.
Bearer-токен требуется в явном заголовке. Браузер не добавляет такой токен автоматически
к чужому запросу. При появлении cookie-аутентификации это решение нужно пересмотреть.
Это одно из трёх узких правил исключения SAST. Ещё два относятся к инвентаризации
эндпоинтов и чтению длины Authorization; они документированы в README и XML-фильтре.

**Почему H2:** база работает в процессе, сохраняет файлы между перезапусками и не требует
Docker или отдельного сервера. Веб-консоль отключена. Это удобный учебный выбор, не гарантия
защиты файлов от пользователя с доступом к компьютеру.

**Почему нет регистрации:** лабораторная требует login. BootstrapUsers создаёт аккаунты
из переменных окружения при первом запуске; публичный endpoint регистрации не нужен.

**CI/CD:** автоматизированы тесты и сканеры при push/PR. Отдельный автоматический деплой
не требуется описанными шагами работы и в проект не добавлен.
