## 1. Цель и устройство проекта

Цель — разработать REST API с аутентификацией, защитой от SQL-инъекций и безопасным выводом пользовательского текста; добавить автоматические проверки тестов, кода и зависимостей при push и pull request.

### Предметная область и контракт

Приложение хранит личные заметки. После входа пользователь получает JWT, создаёт и читает только свои записи. ID владельца определяется сервером по проверенному токену.

| Метод | Назначение | Ответ |
| --- | --- | --- |
| POST /auth/login | Проверка логина и пароля | 200: JWT, Bearer, 900 с |
| GET /api/data | Последние 100 своих заметок | 200: массив items |
| POST /api/notes | Создание своей заметки | 201: созданная запись |

Оба метода /api/* требуют Authorization: Bearer <token>. Неверная аутентификация даёт 401; некорректный JSON — 400; тело более 16 КиБ — 413; превышение лимита входа — 429.

### Стек и структура

Kotlin 2.4.21, Spring Boot 4.1.2, Spring MVC, Spring Security и Nimbus JWT. JSON обрабатывает Jackson 3. Сборка: Gradle Wrapper 8.14.5 и JDK 21. База: встроенная файловая H2, доступ через JdbcTemplate.

ApiController принимает запросы; AuthService проверяет пароль; SecurityConfig валидирует JWT и настраивает фильтры; репозитории выполняют параметризованные SQL-запросы. BootstrapUsers создаёт отсутствующие учебные аккаунты из переменных окружения.

Таблица app_user хранит id, username, password_hash. Таблица note — id, owner_id, title, content, created_at. Внешний ключ связывает заметку с владельцем; индекс (owner_id, id) поддерживает выборку личных данных.

### Запуск и хранение

scripts/run-local.sh скрыто запрашивает учебные пароли alice/bob, генерирует JWT-ключ и запускает Gradle bootRun. API слушает 127.0.0.1:8080; H2 сохраняется в data/lab.mv.db. Веб-консоль и TCP-сервер H2 выключены. Сам интерактивный скрипт не запускался: HTTP-проверка запускала готовый JAR с временными тестовыми данными.

## 2. Реализованные меры защиты

### SQL-инъекции и доступ к записям

JdbcTemplate передаёт значения отдельно от SQL через ?. Создание записи использует PreparedStatement. Пользовательский текст не конкатенируется с SQL. Вход с SQL-подобной строкой сравнивает всю строку с логином и получает 401.

Чтение ограничено WHERE owner_id = ?. Значение берётся из проверенного JWT, а поле owner_id в JSON отклоняется. Поэтому аутентификация дополняется проверкой доступа к данным владельца.

### XSS и валидация

Заметки сохраняются как исходный текст; HtmlUtils.htmlEscape экранирует title/content при выдаче. Строка <script>alert(1)</script> возвращается как &lt;script&gt;alert(1)&lt;/script&gt;. Ответ имеет Content-Type JSON, nosniff и строгую CSP.

HTML-экранирование не универсально для JavaScript, CSS и URL. Будущий клиент обязан учитывать контекст и не вставлять декодированный текст в innerHTML. DTO ограничивают длины; неизвестные поля, неверные типы, хвостовые JSON-токены и чрезмерное тело отклоняются.

### Пароли и JWT

BCrypt с cost=12 хранит соль и хэш. Для нового пользователя требуется минимум 15 символов и максимум 72 байта UTF-8: более длинное значение отклоняется, а не обрезается. Ошибка входа одинакова для неизвестного пользователя и неверного пароля.

JWT подписывается HS256 и действует 900 секунд. Nimbus проверяет подпись; валидаторы проверяют sub, exp, iat, nbf, iss, aud, временные границы и наличие пользователя. Ключ содержит не менее 32 случайных байт. JWT не содержит пароль и не шифрует payload.

### Ограничения модели

Лимит — 10 входов в минуту на IP в одном процессе; он не защищает от распределённого перебора. Нет refresh token, MFA и индивидуального отзыва JWT. Удаление пользователя или смена ключа инвалидируют токены. Для внешней сети нужен HTTPS. CSRF отключён для stateless Bearer API без cookie-аутентификации.

## 3. Автоматические проверки безопасности

Workflow .github/workflows/ci.yml запускает три job при push, pull_request и вручную. Actions закреплены по SHA; GitHub-токен имеет только contents: read. Дистрибутив Gradle проверяется по SHA-256. Автоматический деплой не предусмотрен.

| Job | Проверка | Отчёт |
| --- | --- | --- |
| api-tests | JUnit / Spring MockMvc | HTML и XML |
| sast | SpotBugs 4.10.4 + Find Security Bugs 1.14.0 | main.html, main.xml |
| sca | OWASP Dependency-Check 13.0.0, runtimeClasspath | HTML и JSON |

### SAST

Проверена категория SECURITY со всеми уровнями уверенности. Итог: 27 production class-файлов, 0 находок, ошибок и missing classes. Три узких XML-правила исключения описывают отключённый CSRF, инвентаризацию трёх известных эндпоинтов и чтение длины Authorization.

Ручная конкатенация JSON-ошибок заменена сериализацией, XSS_SERVLET не исключался. ignoreFailures=false сохранён; анализ новых классов и других типов находок не отключён.

### SCA и исправления

Dependency-Check использует публичные NVD feeds, без персонального API-ключа. Анализируются прямые и транзитивные рабочие библиотеки; инструменты сборки и тестовые библиотеки не охвачены. Ошибка анализа и CVSS ≥ 7 блокируют job; отчёт сохраняет также находки ниже порога.

Первый полноценный анализ старых версий дал 252 сопоставления, 46 уникальных CVE. Это сигналы сканера, а не доказательство эксплуатации всех CVE. Выполнен переход на Kotlin 2.4.21, Spring Boot 4.1.2 и Jackson 3; повторные результаты приведены далее. Исключения CVE не добавлялись.

Исправлен пропуск runtimeClasspath из-за родительской конфигурации testAndDevelopmentOnly. После анализа отдельная проверка SHA-256 требует присутствия каждого рабочего JAR в отчёте. Пустой отчёт не может стать успешной проверкой.

## 5. Ответы на контрольные вопросы

### Почему BCrypt предпочтительнее SHA-256?

SHA-256 быстро вычисляется и облегчает массовый перебор. BCrypt увеличивает стоимость каждой попытки и использует случайную соль. Соль делает одинаковые пароли различными по хэшу и мешает применению общих заранее рассчитанных таблиц; она не секретна. Проверка кандидата не требует расшифровки пароля.

### Чем отличаются SAST и DAST?

SAST исследует код без запуска целевого приложения; здесь SpotBugs анализирует JVM-байткод. DAST отправляет запросы работающему приложению и наблюдает ответы. SCA отдельно сопоставляет зависимости с известными уязвимостями. Набор curl-сценариев проверяет конкретное поведение, но не равен полному DAST-аудиту.

### Как работает JWT?

JWT включает header, payload и signature. Base64URL — кодирование, не шифрование. HS256 использует общий секрет для подписи; его держатель может и проверять, и выпускать токены. Сервер должен проверить подпись, алгоритм, обязательные claims, время, issuer и audience.

Кража действующего JWT позволяет выполнять действия до истечения срока или иной потери валидности. В проекте нет индивидуального отзыва; смена общего ключа инвалидирует все старые токены. Подпись не заменяет защищённый транспорт HTTPS.

### Какие риски возникают без аудита зависимостей?

Уязвимость в прямой или транзитивной библиотеке может привести к обходу доступа, утечке, выполнению кода или отказу в обслуживании. SCA выявляет известные проблемы и помогает выбрать исправленные версии. Ошибочная настройка охвата способна дать ложный зелёный результат, поэтому важно проверять состав отчёта.
